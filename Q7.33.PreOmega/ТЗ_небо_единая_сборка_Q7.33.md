# Часть I. Общие положения

## 1. Цель

Собрать одно небо из лучшего в обоих проектах: математика и наполнение — из B, архитектура, имена, раскладка папок и модель управления — из A. Результат: одна папка `SkyEnvironment/`, два контроллера с непересекающимися адресами записи, десять пресетов-ресурсов, рабочая ингейм-панель настройки градиента, ноль мёртвого кода.

## 2. Задачи

1. Перенести живое небо B в структуру папок A.
2. Удалить вуаль и всё, что с ней связано, сохранив задел для будущих облаков.
3. Устранить четыре дефекта градиента и небесных тел (мёртвая зона рампы, мёртвое первое окно, вторая луна, зависимость яркости от высоты солнца).
4. Перевести рампу целиком на данные: ноль констант в шейдере.
5. Разделить запись в материал и запись в свет сцены между двумя контроллерами.
6. Переложить таблицы-константы из кода панели B в ресурс-пресеты.
7. Сделать панель настройки градиента с процентными созависимыми стопами и замочками.
8. Вычистить мёртвый код, битые сцены и архивные патчи.

## 3. Вне объёма этого ТЗ

Отдельные задачи, см. главу 11:

- **Облака.** В сборке Q7.33 облаков нет. Единственный живой облачный слой B — вуаль — удалён; вторая облачная система мертва. Облака делаются отдельным скриптом.
- **Луна днём.** Полнолуние будет видно на дневных ключах; приглушение до «слабо читается» — отдельным шагом.
- **Суточный цикл.** Интерполятор пресетов поверх готовых контроллеров.
- **Возврат вуали.** Возможен из архива, но не в этой сборке.

| Компонент | Адрес записи | Объём | Знает о |
|---|---|---|---|

**Правило:** ни один узел, кроме двух контроллеров, не вызывает `set_shader_parameter` и не трогает `DirectionalLight3D`.

**Почему разделено** (решение 14):

| | Палитра / градиент | Освещение |
|---|---|---|
| Что это | данные | состояние сцены |
| Когда меняется | при загрузке пресета | каждый кадр, если есть суточный цикл |
| Куда пишет | `ShaderMaterial` | `DirectionalLight3D`, `WorldEnvironment` |
| Зависимости | только материал | только узлы сцены |
| Как тестируется | headless, CPU-зеркалом | только в сцене |

`VeilSkyPanel` в B разросся до 1133 строк именно потому, что в одном файле смешаны UI, палитра, форма градиента, положение источника, ориентация света, энергия света, свет земли и вуаль.

Практический выигрыш: небо проверяется без сцены; подбор энергии света — правка одного Resource; суточный цикл дёргает `apply_palette()` и `apply_light()` независимо с разной частотой; облака придут как третий адрес записи со своим контроллером и не полезут ни в палитру, ни в свет.

**Граница дробления:** два адреса записи — два контроллера. Дальше делить нельзя: `SkyPaletteController` + `SkySourceController` + `SkyStarController` — это три писателя одного материала, то есть ровно та проблема, от которой уходим.

# Часть III. Технические требования

## 11. Шейдер `SkyEnvironment.gdshader`

### 11.1. Метрика — не трогаем

`u_ellip()` остаётся как есть. Обоснование замерами:

- `u(−s) = 1.00000` на всех 19 контрольных высотах солнца;
- в плоскости солнца `u = угол/π` точно: u(30°) = 0.166667, u(90°) = 0.5, u(180°) = 1.000000;
- у полюса растяжение `S → 1.0`, метрика не вырождается;
- HEAD r11_s4 метрически идентичен патчу r12_s3: max |Δu| = 2.22e-16 на сетке 91×121×37 высот солнца.

### 11.2. Вуаль — удалить

| Где | Что | Объём |
|---|---|---|
| uniform'ы | `hc_*` (17 шт.), `veil_*` (7 шт.), строки 304–345 | ~42 строки |
| модуль `SKYHC-1` | `slab_interval`, `hc_density`, `hc_alpha` + хелперы, строки 598–714 | ~117 строк |
| `sky()` | `hc_a/hc_d/hc_tau`, `veil_a`, `sun_mask`, `veil_col`, `base_lin`, `msheen`, ветка `hc_diag` | ~25 строк |
| текстуры | `uniform sampler3D noise_pw`, `noise_worley` | 2 строки |
| материал | все `shader_parameter/hc_*` и `veil_*` | — |

Перестаёт работать: `hc_debug` 1/2/3 (замена — `sky_debug_mode`, п. 11.8), лунный шеен на вуали, дрейф поля от ветра.

### 11.3. Луна — без фаз, без копии

**Удалить:** `uniform float moon_phase`; `dist = mix(0.0, 2.2 * r, clamp(moon_phase, …))`; `cut = smoothstep(-w, w, length(p - vec2(dist, 0.0)) - r * 0.98)`; `crescent = body * cut`; `earthshine = body * (1.0 - cut) * 0.06`; `det_w = smoothstep(0.85, 0.95, moon_phase) * moon_detail_int`; гейт `if (mvis <= 0.0 || moon_phase <= 0.001)`.

Earthshine (подсветка тени серпа земным отражением, 0.06) теряет смысл — тени серпа больше нет.

**Новая реализация** — та же структура, что у `sun_celestial`: направление аргументом, угловое расстояние, ранний выход, `fwidth` по углу.

```glsl
// Луна — диск + кратеры + ореол. Фаз нет: всегда полная (решение 10).
// Гашение задней полусферы — тем же механизмом, что у солнца: угловое расстояние.
vec3 moon_celestial(vec3 dir, vec3 md_in) {
    vec3 md = normalize(md_in);
    float r = max(moon_size, 0.001);

    float ang = acos(clamp(dot(dir, md), -1.0, 1.0));
    float edge = max(fwidth(ang) * 1.5, 0.0004);
    if (ang > 2.5 * r + edge) {
        return vec3(0.0);                       // задняя полусфера мертва
    }

    vec3 up0 = abs(md.y) > 0.99 ? vec3(0.0, 0.0, 1.0) : vec3(0.0, 1.0, 0.0);
    vec3 right = normalize(cross(up0, md));
    vec3 up = cross(md, right);
    vec2 p = vec2(dot(dir, right), dot(dir, up));

    float body = 1.0 - smoothstep(-edge, edge, ang - r);   // crisp-кромка по углу

    float det = 1.0;
    if (moon_detail_int > 0.001) {
        vec2 muv = clamp(p / r * 0.5 + 0.5, vec2(0.0), vec2(1.0));
        det = mix(1.0, texture(moon_detail_tex, muv).r * 1.7, moon_detail_int);
    }

    float mdot = max(dot(dir, md), 0.0);
    vec3 mgcol = mix(moon_color, filmic3(sk_mid), 0.55);
    return moon_color * (body * det)
         + mgcol * (pow(mdot, moon_glow_exp) * moon_glow_int);
}
```

**Диагноз исходного бага.** Луна была построена через проекцию на касательную плоскость: `p = vec2(dot(dir, right), dot(dir, up))`, `body = 1 - smoothstep(-w, w, length(p) - r)`. `length(p)` — расстояние до **оси** через центр сферы по направлению `md`; оно одинаково для `dir = md` и для `dir = -md`. Проверки «точка спереди» не было.

Замер (порт математики шейдера, `moon_size = 0.02`, `moon_phase = 0.6`):

| Положение луны | crescent в луне | crescent в антиподе | dot(dir, md) в антиподе |
|---|---|---|---|
| elev 50°, azim 0° | 1.000 | **1.000** | −1.000 |
| elev 30°, azim 90° | 1.000 | **1.000** | −1.000 |
| elev 10°, azim 200° | 1.000 | **1.000** | −1.000 |
| elev 60°, azim 45° | 1.000 | **1.000** | −1.000 |

Ореол не зеркалил (`mdot = max(dot(dir, md), 0.0)` обнуляет заднюю полусферу), поэтому копия выглядела тусклее: серп без ореола. Карта кратеров на задней полусфере была зеркальной.

**Как солнце гасит свою копию** — оно построено через угловое расстояние, а не через проекцию: `ang = acos(clamp(dot(dir, sd), -1.0, 1.0))`, `disc = 1.0 - smoothstep(sunR - edge, sunR + edge, ang)`. На антиподе `ang = 180°`, `sunR = 1.8°` — `smoothstep` далеко за правым краем, `disc = 0`. Формула считает «насколько я далеко от солнца в градусах», а не «насколько далеко от оси».

**Что даёт новая реализация сверх фикса:**

- копия исчезает на всей задней полусфере, а не только в антиподе (раньше вторая луна рисовалась и под углом — `length(p)` мал для всего кольца вокруг антипода);
- crisp-кромка на любом разрешении: `fwidth(ang)` вместо `fwidth(p.x)`, производная от проекции у горизонта деградирует;
- ранний выход по углу: 99.9% пикселов не считают `cross()`, `texture()`, `pow()`;
- зеркальная карта кратеров уходит вместе с веткой;
- сигнатура `moon_celestial(dir, md)` — как `sun_celestial(dir, sd)`, одна конвенция на два тела.

**Побочный эффект.** В `SUNMOON` у K3–K6 `mphase = 0.0` — на дневных ключах луна сейчас невидима именно фазой. После удаления фаз она станет видимой всегда. Это соответствует решению 2. Инструмент приглушения уже в данных: `moon_glow_int` = 0.35/0.2/0.1 для K0/K1/K2 и 0.0 для K3–K6; `moon_color` в display-space на ярком небе читается слабо. Отдельная ручка — глава 11.4, задача З-2.

### 11.4. Отложено: луна днём

Решение 2, вторая часть: луна в дневных пресетах должна слабо читаться. Задача **З-2** после приёмки сборки: добавить `sk_moon_day_fade` — подмешивание цвета луны к `sky_palette(dir)` в точке луны, чтобы тело читалось как «через дымку», а не как дырка в небе.

### 11.5. Рампа — всё на данных, ноль констант

**Исходный дефект.**

```glsl
vec3 c = sk_glow_col;
c = mix(c, sk_horizon,   smoothstep(sk_p1, max(sk_p2, sk_p1 + 0.005), u));
c = mix(c, sk_band_col,  smoothstep(sk_p2, max(sk_p3, sk_p2 + 0.005), u));
c = mix(c, sk_band2_col, smoothstep(sk_p3, max(sk_p4, sk_p3 + 0.005), u));
c = mix(c, sk_mid,       smoothstep(sk_p4, max(sk_p5, sk_p4 + 0.005), u));
c = mix(c, sk_anti_col,  smoothstep(0.75, 0.97, u));      // ← константы
```

Три проблемы: последнее окно — литералы; окно не дотянуто до конца шкалы; **дыра между `sk_p5` и 0.75** — участок не принадлежит ни одному окну (четыре `k` уже равны 1, терминальное ещё 0).

Замер (K4, дефолт материала, `sk_p5 = 0.520`):

| u | L | k_mid (окно p4→p5) | k_term (окно 0.75→0.97) |
|---|---|---|---|
| 0.50 | 0.039403 | 0.9767 | 0.0000 |
| **0.52** | **0.038796** | 1.0000 | 0.0000 |
| **0.60** | **0.038796** | 1.0000 | 0.0000 |
| **0.70** | **0.038796** | 1.0000 | 0.0000 |
| **0.75** | **0.038796** | 1.0000 | 0.0000 |
| 0.80 | 0.036615 | 1.0000 | 0.1315 |
| 0.97 | 0.022208 | 1.0000 | 1.0000 |
| 1.00 | 0.022208 | 1.0000 | 1.0000 |

Ровно постоянно на **[0.52, 0.75] = 93.6° → 135°, то есть 41.4° неба одного цвета.**

| Ключ | `sk_p5` | Дыра | В градусах |
|---|---|---|---|
| дефолт материала, K3, K4, K5, K6 | 0.520 | 0.520 → 0.750 | **41.4°** |
| K1, K2 | 0.600 | 0.600 → 0.750 | **27.0°** |
| K0 | 0.750 | нет | — (но окно терминала стартует с ненулевой скоростью — угол) |

Хвост [0.97, 1.0] тоже постоянен, но он 5.4°. Участок 0.75 → 0.97 меняется (0.0388 → 0.0222, −43%), просто медленно.

**Новая реализация.**

```glsl
uniform float sk_p1 : hint_range(0.0, 1.0);   // ядро зари → горизонт
uniform float sk_p2 : hint_range(0.0, 1.0);   // горизонт → пояс 1
uniform float sk_p3 : hint_range(0.0, 1.0);   // пояс 1 → пояс 2
uniform float sk_p4 : hint_range(0.0, 1.0);   // пояс 2 → середина
uniform float sk_p5 : hint_range(0.0, 1.0);   // середина → антисоляр (начало)
uniform float sk_p6 : hint_range(0.0, 1.0);   // антисоляр (конец); 1.0 = самый плавный уход
uniform float sk_sharp : hint_range(0.05, 1.0) = 1.0;

float win(float lo, float hi, float x) {
    float w = (hi - lo) * sk_sharp;          // окно прижато к ПРАВОМУ стопу
    return smoothstep(hi - w, hi, x);
}

vec3 ramp_u(vec3 dir, vec3 sd) {
    float u = u_ellip(dir, sd);
    vec3 c = sk_glow_col;
    c = mix(c, sk_horizon,   win(sk_p1, sk_p2, u));
    c = mix(c, sk_band_col,  win(sk_p2, sk_p3, u));
    c = mix(c, sk_band2_col, win(sk_p3, sk_p4, u));
    c = mix(c, sk_mid,       win(sk_p4, sk_p5, u));
    c = mix(c, sk_anti_col,  win(sk_p5, max(sk_p6, 1.0), u));
    return c;
}
```

- Никаких `max(sk_pN, sk_pN-1 + 0.005)` — порядок шейдер не проверяет и не чинит.
- Никаких литералов. Единственное число в теле — `1.0` как конец шкалы; это не настройка, это определение u.
- Дыра невозможна структурно: окно каждого перехода заканчивается ровно в своём стопе, последнее — ровно в 1.0. Шкала покрыта целиком при любых данных.
- Если данные придут неупорядоченными, `smoothstep` с `e0 > e1` даст ступеньку — не аварию и не молчаливый баг. Порядок обеспечивают панель (п. 13.4) и валидатор (глава 15). Шейдер — тупой исполнитель.

**Резкость переходов.** Ширина окна сейчас жёстко равна расстоянию между стопами; отдельной ручки нет — чтобы сделать переход резче, надо двигать стоп, а это меняет всю раскладку. `sk_sharp`:

| `sk_sharp` | Что происходит |
|---|---|
| 1.0 | окно на всю дистанцию до стопа — нынешнее поведение, побитово |
| 0.5 | окно в два раза уже, переход резче |
| 0.1 | почти ступенчатая картинка, 6 дискретных цветов |

Окно прижато к правому стопу, поэтому положение цветов на шкале не плывёт при изменении резкости. Если понадобится разная резкость по участкам — `sk_sharp` расширяется до `sk_sharp1…sk_sharp5`, форма `win()` позволяет.

### 11.7. Ореол источника и стрик

Один uniform `sk_glow_col` отвечает за три вещи: стоп 0 рампы, цвет ореола в `sky_palette`, цвет ореолов и стрика в `sun_celestial`. Нельзя сделать «золотой блик вокруг диска» и «глубоко-красный пояс у горизонта» одновременно.

```glsl
uniform vec3 sk_glow_col : source_color;   // стоп 0 рампы
uniform vec3 sk_halo_col : source_color;   // ореол источника + стрик
```

Два независимых uniform'а, никакого коэффициента связи. В `sky_palette` и `sun_celestial` — `sk_halo_col` вместо `sk_glow_col`.

Границы гейта стрика — в uniform'ы (решение 3: никаких зашитых градусов):

```glsl
uniform float sk_streak_gate_lo : hint_range(0.0, 180.0) = 45.0;
uniform float sk_streak_gate_hi : hint_range(0.0, 180.0) = 60.0;
float sgate = 1.0 - smoothstep(radians(sk_streak_gate_lo), radians(sk_streak_gate_hi), ang);
```

Сам гейт оставляем — без него спрайт стрика сходится в центр на антисоляре, блик лезет на противоположную сторону купола (в коде B есть соответствующий комментарий «ФИКС: стрик только вблизи источника»).

### 11.8. `low_dim` — удалить без замены

**Удалить:**

```glsl
// sky_palette()
float low = 1.0 - smoothstep(0.0, 20.0, sd.y);
base *= 1.0 - sk_low_dim * low;
```

плюс `uniform float sk_low_dim`, поле `low_dim` в `SHAPE[*]`, ключ в `SHAPE_KEYS`. **Множитель взамен не вводится.** `sky_energy` из A тоже не переносится.

Яркость купола задаётся только шестью цветами стопов. Они и так per-key и уже HDR: `PAL[K1].glow = (1.693, 0.361, 1.693)`, `PAL[K4].glow = (1.495, 0.059, 0.027)`. Тёмная ночь получается тёмными цветами, а не умножением светлых на 0.7.

**Компенсация при переносе палитр.** Сейчас итоговая яркость = палитра × `low_dim`. Если перенести `PAL` как есть, небо станет светлее. Поэтому при переносе (шаг E2) цвета домножаются на прежний коэффициент — однократно, в данных, без нового uniform'а:

| Ключ | высота солнца | `low_dim` | множитель `1 − low_dim·low` |
|---|---|---|---|
| K0 | −30.0° | 0.30 | **0.700** |
| K1 | −13.5° | 0.25 | **0.750** |
| K2 | −5.0° | 0.22 | **0.780** |
| K3 | +0.3° | 0.25 | **0.752** |
| K4 | +0.5° | 0.25 | **0.753** |
| K5 | +4.0° | 0.25 | **0.785** |
| K6 | +15.0° | 0.25 | **0.938** |

Между шагом C6 (удаление из шейдера) и шагом E2 (перенос палитр) небо на дефолте материала будет ярче прежнего. Это ожидаемое промежуточное состояние, фиксируется в плане.

**Про «сцену освещает снизу» и «ночь не случится».** `low_dim` этого не лечил — он умножал цвет неба в шейдере, а за освещение сцены отвечает `DirectionalLight3D`. Ночь обеспечивается:

- `key_energy` в пресете — энергия `SunLight` (`GROUND[K0].e = 0.097` против `2.2` у K4, в 22 раза темнее);
- `moon_light_energy` в пресете — энергия `MoonLight`, дефолт 0.12;
- высотой солнца — направление света и теней;
- палитрой — яркость самого купола.

Света из-под земли нет: `SunLight` смотрит туда, где солнце (ниже горизонта → светит вверх, земля не освещена), энергия на ночных пресетах около нуля. `MoonLight` смотрит на луну, она над горизонтом.

### 11.10. Итоговый `sky()`

```glsl
void sky() {
    vec3 dir = normalize(EYEDIR);
    vec3 sd  = normalize(sk_sun_dir);
    vec3 md  = normalize(sk_moon_dir);

    vec3 col = sky_palette(dir);
    col += sun_celestial(dir, sd) + moon_celestial(dir, md);

    float horfade = smoothstep(-0.05, 0.15, dir.y);
    float mdamp = 1.0 - smoothstep(-0.02, 0.02, md.y) * pow(max(dot(dir, md), 0.0), 8.0) * 0.7;
    col += vec3(0.85, 0.90, 1.0) * (star_field(dir) * star_intensity * horfade * mdamp);

    vec3 disp = filmic3(col);
    COLOR = comp_linear ? srgb_to_linear3(disp) : inv_filmic3(disp);
}
```

Режим отладки:

```glsl
uniform int sky_debug_mode : hint_range(0, 2) = 0;   // 0 = небо, 1 = u, 2 = номер сегмента
```

- **1** — `COLOR = vec3(u)`: серая карта шкалы по куполу. Видна форма изолиний, где реально встаёт антисоляр, где плоские зоны.
- **2** — `COLOR` по номеру окна перехода: шесть различимых оттенков, фактическая раскладка стопов.

### 12.3. Знак ориентации света — проверить и починить

В A:

```gdscript
var ray_direction := -direction.normalized()          // direction = НА источник
light.global_basis = Basis.looking_at(ray_direction, up)
```

Конвенция Godot: свет излучает вдоль **−Z** своего базиса ([доки](https://docs.godotengine.org/en/stable/classes/class_directionallight3d.html)), а `Basis.looking_at(target)` направляет **−Z** на `target`. Здесь `target = −источник`, значит −Z смотрит от источника и свет уходит в небо: при солнце на +10° сцена освещена как при −10°.

Правка — убрать минус: `Basis.looking_at(direction.normalized(), up)`. Комментарий в A («Direction указывает от наблюдателя к источнику. Световые лучи идут в обратную сторону») описывает верную идею, но `looking_at` принимает цель, а не направление луча — минус лишний.

**Тест (шаг D2):** солнце elev 60° azim 0° → `light.global_transform.basis.z` совпадает с `_direction(0, 60)` до 1e-5. Прогнать на elev ∈ {−90, −45, 0, 45, 89.9, 90}. Если в текущей сборке A тени падают правильно — значит конвенция иная, строку не трогаем; тест выясняет это за один запуск.

### 13.2. Полоса рампы

Горизонтальная полоса, рисуется когда вкладка видима. Для каждого пикселя x: `u = x / width`, цвет = CPU-зеркало `ramp_u(u)` (~40 строк GDScript, формулы те же, что в `sky_grad_check.py`). Зеркало одно на панель и валидатор.

### 13.3. Режим «масштаб»

Слайдер 0.5×…2.0× растягивает/сжимает все свободные стопы от центра шкалы, залоченные стоят. Нужен, чтобы «раздвинуть градиент» целиком, не ломая форму.

### 13.4. Маркеры, замочки, проценты (решение 4)

Позиции хранятся и отображаются в процентах (0…100), в шейдер пишутся долями. У каждого стопа чекбокс-замочек.

Алгоритм при перетаскивании стопа `i` в позицию `q`:

```
1. q зажимается между ближайшими ЗАЛОЧЕННЫМИ соседями
   (lo = залоченный слева или 0%, hi = залоченный справа или 100%),
   MIN_GAP = 1% шкалы

2. свободные стопы делятся на две группы: слева от i и справа

3. каждая группа пересчитывается так, чтобы сохранить ПРЕЖНИЕ ПРОПОРЦИИ
   между соседями и уложиться в свой интервал:
	  LEFT  → интервал (lo, q)
	  RIGHT → интервал (q, hi)

4. запись одним пакетом через контроллер
```

Пример: замок на стоп 3, тянем стоп 2 вправо → стоп 3 стоит, стопы 0 и 1 сдвигаются влево пропорционально своим долям, стопы 4 и 5 — вправо, сжимаясь к стопу 6.

В шейдере от механизма ничего нет: он живёт в панели, в пресете хранятся абсолютные позиции, пресет не зависит от способа редактирования. Порядок стопов гарантирован тем, что маркеры физически не переходят друг через друга (`MIN_GAP`), — поэтому в шейдере не нужны ни `max()`, ни clamp'ы.

### 13.5. Сохранение пресета из панели

Статические функции. Вызывается из панели при сохранении пресета и из harness'а. Ошибки блокируют сохранение, предупреждения — нет.

| Проверка | Уровень | Условие |
|---|---|---|
| Порядок стопов | **ошибка** | `p1 < p2 < p3 < p4 < p5 < p6`, зазор ≥ 0.01 (тот же `MIN_GAP`, что в панели) |
| Соседние цвета не совпадают | **ошибка** | для всех пяти пар `color(i) != color(i+1)` побитово |

| `light` не задан | **ошибка** | пресет без профиля света не применяется |
| `p6 < 1.0` | предупреждение | терминал не дотянут до антисоляра — останется плоский хвост |
| Ширина окна | предупреждение | `(pN − pN-1) × sharp < 0.02` — переход почти скачком |
| Пересвет | предупреждение | любой канал цвета > 2.5 |
| `sun_elevation < 0` при `sun_enabled` | предупреждение | солнце под горизонтом видно (решения 2 и 16) — проверить, что так задумано |

## 19. Что НЕ делаем

1. **Не переносим рампу A целиком.** У A 4 стопа против 6, нет ореола источника, HDR-ядра, dither, стрика, кратеров. Забираем только принцип «окно последнего сегмента дотянуто до конца шкалы».
2. **Не сохраняем логику B по положению источника.** Клампы `-35…89.5`, переключение света на луну при `-2°`, `BounceLight`, один свет на два источника — выбрасываются (решение 5).
3. **Не вводим множитель яркости взамен `low_dim`.** Ни `dome_mult`, ни `sky_energy`. Яркость купола — это шесть цветов стопов (решение 9).
4. **Не оставляем фазы луны «на всякий случай».** Удаляются полностью: uniform, SDF-cut, earthshine, `mphase` в данных, поле в пресете (решение 10).
5. **Не применяем патч `Q7.32_SkyLight_r12_s3_spheremetric.patch`.** Метрически идентичен HEAD (max |Δu| = 2.22e-16 на сетке 91×121×37), снят с ветки до r10_s4 — вернул бы `wedge`/`below`/`zen_w`.
6. **Не трогаем метрику `u_ellip`.** `u(−s) = 1.00000` на всех 19 контрольных высотах; в плоскости солнца `u = угол/π` точно; у полюса `S → 1.0`, метрика не вырождается.
7. **Не возвращаем `wedge`, `zen_w`, `below`.** Удалены как костыли в r10_s4.
8. **Не вводим веток по номеру ключа в шейдер.** Различия между ключами — только данные.
9. **Никаких констант в рампе.** Ни «0.75», ни «0.97», ни «+0.005», ни `max()`-страховок порядка. Порядок обеспечивают панель и валидатор.
10. **Не дробим контроллеры дальше двух.** Два адреса записи — два контроллера (п. 9).
11. **Не делаем в этом ТЗ:** облака, луну днём, суточный цикл, возврат вуали.
